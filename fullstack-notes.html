Part A — Web Development Foundations

1. What is Full Stack Web Development?

A "Full Stack" developer can build both sides of a web application: the Frontend (everything the user sees and interacts with in the browser) and the Backend (the server, database, and business logic behind the scenes) – plus knows enough about how they connect and deploy together to ship a complete, working product alone.

  • This course's stack: HTML/CSS/JavaScript for the frontend, and Python with Django for the backend – one of the most popular, in-demand combinations for web development jobs.
  • Django is a "batteries-included" framework: it comes with an ORM, admin panel, authentication, and forms built in, letting a solo developer or small team build production-ready applications fast.

2. How the Web Works

Core Interview Concept

Understanding this request/response cycle is fundamental to everything that follows in this course.

  • A user types a URL (or clicks a link) in their browser (the Client).
  • The browser looks up the domain's IP address via DNS (Domain Name System), then sends an HTTP Request to the Server at that address.
  • The server processes the request (often involving a database), and sends back an HTTP Response – usually HTML, CSS, JavaScript, or JSON data.
  • The browser receives the response and renders it into the visible page the user sees.
  • HTTP Methods: GET (retrieve data), POST (submit/create data), PUT/PATCH (update data), DELETE (remove data) – the foundation of REST APIs (Part J).
  • HTTP Status Codes: 200 (OK), 201 (Created), 301/302 (Redirect), 400 (Bad Request), 401/403 (Unauthorized/Forbidden), 404 (Not Found), 500 (Server Error).

3. Frontend vs Backend

  • Frontend – runs INSIDE the user's browser: HTML (structure), CSS (styling), JavaScript (interactivity). The user can view its source code directly.
  • Backend – runs ON THE SERVER, invisible to the user: handles business logic, talks to the database, enforces security/permissions, and returns data or rendered pages to the frontend.
  • Database – where data is permanently stored (Part G) – the backend reads from and writes to it, the frontend never accesses it directly.

6. Introduction to HTML

Frontend

HTML (HyperText Markup Language) defines the STRUCTURE and CONTENT of every web page – headings, paragraphs, images, links – using "tags" that wrap around content to describe what it is.

  • Most tags come in pairs: an opening tag <p> and a closing tag </p>, wrapping the content between them.
  • Some tags are "self-closing" (no content to wrap), e.g. <img>, <br>, <input>.
  • Tags can have "attributes" providing extra information, e.g. <img src="photo.jpg" alt="A photo">.

Part C — CSS Fundamentals

14. Introduction to CSS

Frontend

CSS (Cascading Style Sheets) controls the VISUAL PRESENTATION of HTML – colors, spacing, fonts, layout – keeping structure (HTML) and styling (CSS) cleanly separated.

  • Inline – <p style="color: red;">, applied directly to one element; avoid in real projects.
  • Internal – a <style> block inside the HTML <head>; fine for small pages/demos.
  • External – a separate .css file linked via <link>; the standard, recommended approach for any real project.
<!-- In the HTML <head>: -->
<link rel="stylesheet" href="styles.css">

/* In styles.css: */
p {
    color: red;
    font-size: 16px;
}

15. CSS Selectors

Frontend

Selectors determine WHICH HTML elements a CSS rule applies to.

p { color: navy; }                  /* every <p> element */
.highlight { background: yellow; }  /* every element with class="highlight" */
#main-title { font-size: 32px; }    /* the one element with id="main-title" */
div p { margin: 10px; }             /* every <p> INSIDE a <div> (descendant) */
div > p { margin: 10px; }           /* every <p> that is a DIRECT child of a <div> */
a:hover { color: red; }             /* a link, only while the mouse hovers over it */
input:focus { border-color: blue; } /* an input, only while it's actively selected */
li:first-child { font-weight: bold; } /* the first <li> in its parent */
  • Specificity – when multiple rules could apply to the same element, ID selectors beat class selectors, which beat tag selectors – the most specific rule wins.

16. The Box Model

FrontendCore Interview Concept

Every HTML element is treated as a rectangular box made of four layers, from inside out – understanding this is essential for controlling spacing and layout precisely.

  • Content – the actual text/image inside the element.
  • Padding – space between the content and the border (inside the box).
  • Border – a visible (or invisible) line around the padding.
  • Margin – space OUTSIDE the border, between this element and its neighbors.
  • box-sizing: border-box; – a very commonly used reset making width/height include padding and border (rather than adding on top of them), avoiding a lot of layout confusion – often applied globally to every element in real projects.
* { box-sizing: border-box; }

.card {
    width: 300px;
    padding: 20px;
    border: 2px solid #ccc;
    margin: 15px;
}

18. Layout with Flexbox

FrontendWidely Used

Flexbox arranges items in a single row or column, distributing space and alignment intelligently – the standard tool for navigation bars, card rows, and centering content.

.container {
    display: flex;
    justify-content: space-between;  /* spacing along the main axis */
    align-items: center;              /* alignment along the cross axis */
    gap: 20px;                        /* space between each item */
}

.item {
    flex: 1;   /* this item grows/shrinks to fill available space equally */
}
  • flex-direction: row (default, horizontal) or column (vertical).
  • justify-content – controls spacing: flex-start, center, space-between, space-around.

19. Layout with CSS Grid

Frontend

20. Responsive Design & Media Queries

FrontendFrequently Tested

Responsive design means a page adapts its layout to different screen sizes (desktop, tablet, mobile) – essential, since the majority of web traffic today is on mobile devices.

.container {
    display: flex;
    flex-direction: row;
}

/* Below 768px wide (typical tablet/mobile breakpoint), stack items vertically instead */
@media (max-width: 768px) {
    .container {
        flex-direction: column;
    }
    h1 {
        font-size: 24px;   /* smaller heading on small screens */
    }
}
  • Always include <meta name="viewport" content="width=device-width, initial-scale=1.0"> in the HTML head (Section 7) – without it, mobile browsers render the page at desktop width and zoom out, breaking media queries.

29. Fetch API & AJAX Basics

FrontendConnects to Part J (Django APIs)

The Fetch API lets JavaScript make HTTP requests directly from the browser, WITHOUT a full page reload – the technique that powers dynamic pages loading data in the background (AJAX = Asynchronous JavaScript And XML, though JSON is standard today, not XML). This is exactly how a JavaScript frontend talks to a Django REST API (Section 66).

fetch("https://api.example.com/posts/")
    .then(response => response.json())
    .then(data => {
        console.log(data);
    })
    .catch(error => console.error("Error:", error));

// Modern async/await syntax (equivalent, often cleaner to read):
async function loadPosts() {
    const response = await fetch("https://api.example.com/posts/");
    const data = await response.json();
    console.log(data);
}
loadPosts();

// Sending data with a POST request:
async function createPost(title, content) {
    const response = await fetch("https://api.example.com/posts/", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ title: title, content: content })
    });
    const data = await response.json();
    console.log("Created:", data);
}

35. What is Django? The MVT Architecture

BackendCore Interview Concept

Django is a high-level Python web framework that encourages fast, clean development with a "batteries-included" philosophy: an ORM, admin panel, authentication, and form handling all come built in, so you rarely need third-party packages just to get started.

  • Django follows the MVT (Model-View-Template) pattern – its own take on the more widely-known MVC pattern.
  • Model – defines the data structure and talks to the database (Part G).
  • View – contains the logic: receives a request, talks to Models as needed, and decides what response to send back (Section 40).
  • Template – the HTML file that defines how data is displayed to the user (Section 41).
  • A commonly asked interview distinction: in Django's MVT, the framework itself handles the URL-to-view dispatching (what a traditional "Controller" would do), so the developer mainly writes Models, Views, and Templates.

39. URLs & URL Routing

Backend

Django matches an incoming URL against a list of patterns to decide which View function should handle it – typically organized with the project's urls.py delegating to each app's own urls.py.

# blog/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("", views.post_list, name="post-list"),
    path("post/<slug:slug>/", views.post_detail, name="post-detail"),
]
# myblog/urls.py (the project's top-level routing)
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("blog.urls")),   # delegates any other URL to blog/urls.py
]
  • <slug:slug> – a "path converter" capturing part of the URL as a variable, passed directly into the view function. Other converters: <int:pk>, <str:name>.
  • The name="post-detail" argument lets templates and Python code reference this URL by name (Section 41) rather than hard-coding the path – so the URL can change later without breaking every link to it.

40. Views (Function-Based Views)

Backend

A View is a Python function (or class, Section 55) that takes a web request and returns a web response – where the actual page logic lives.

# blog/views.py
from django.shortcuts import render, get_object_or_404

def post_list(request):
    posts = Post.objects.filter(published=True)
    return render(request, "blog/post_list.html", {"posts": posts})

def post_detail(request, slug):
    post = get_object_or_404(Post, slug=slug, published=True)
    return render(request, "blog/post_detail.html", {"post": post})
  • render(request, template_name, context_dict) – the most common return pattern: combines a template with data (the "context" dictionary) and returns the resulting HTML.
  • get_object_or_404(Model, **kwargs) – fetches one object, or automatically returns a proper 404 "Not Found" page if it doesn't exist, instead of crashing with an error.

    <h2><a href="{% url 'post-detail' post.slug %}">{{ post.title }}</a></h2>
    <p>By {{ post.author.username }} on {{ post.created_at|date:"F j, Y" }}</p>
    <p>{{ post.content|truncatewords:20 }}</p>
  </article>
{% empty %}
  <p>No posts yet.</p>
{% endfor %}
{% endblock %}
  • {{ variable }} – outputs a value. {% tag %} – template logic (loops, conditionals, template inheritance).
  • {% extends %} / {% block %} – template inheritance: a child template fills in named "blocks" defined by a shared parent, avoiding repeating the same HTML layout on every page.
  • | pipes to a "filter" that transforms the value for display, e.g. |date:"F j, Y" or |truncatewords:20.
  • {% url 'name' arg %} – generates the correct URL by its name (Section 39), rather than hard-coding the path.

Part G — Django Models & Database

44. Introduction to the Django ORM

DatabaseCore Django Skill

The ORM (Object-Relational Mapper) lets you work with the database using Python classes and objects instead of writing raw SQL – a Python class becomes a database table, and each instance of that class becomes one row.

  • Django defaults to SQLite for development (a simple, file-based database, zero setup required) and supports PostgreSQL/MySQL for production (Section 69).
  • The ORM works identically regardless of which database is configured underneath – you write the same Python either way.

45. Creating Models

Database

A Model is a Python class inheriting from models.Model; each class attribute defines one database column.

# blog/models.py
from django.db import models
from django.contrib.auth.models import User
from django.urls import reverse

class Category(models.Model):
    name = models.CharField(max_length=100)

    def __str__(self):
        return self.name

class Post(models.Model):
    title = models.CharField(max_length=200)
    slug = models.SlugField(unique=True)
    author = models.ForeignKey(User, on_delete=models.CASCADE, related_name="posts")
    category = models.ForeignKey(Category, on_delete=models.SET_NULL, null=True, blank=True)
    content = models.TextField()
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)
    published = models.BooleanField(default=True)

    class Meta:
        ordering = ["-created_at"]   # newest posts first, by default

    def __str__(self):
        return self.title

    def get_absolute_url(self):
        return reverse("post-detail", kwargs={"slug": self.slug})
  • __str__ – defines how an object displays as text (e.g. in the Django Admin and the shell) – always define this, or every object shows as an unhelpful "Post object (1)".
  • get_absolute_url() – a convention returning the canonical URL for one object, used by {{ post.get_absolute_url }} in templates and by the admin's "View on site" link.

46. Migrations

DatabaseDaily Command

Migrations are Django's version-control system for the database schema – every time a Model changes, a migration file records exactly what changed, and can be applied (or reversed) safely.

python manage.py makemigrations blog
# Migrations for 'blog':
#   blog/migrations/0001_initial.py
#     + Create model Category
#     + Create model Post
#     + Create model Comment

python manage.py migrate
# Actually applies the migration, creating/altering the real database tables
  • makemigrations – generates the migration FILE (a plan), based on changes detected in models.py.
  • migrate – actually EXECUTES that plan against the database.
  • Always run both commands, in that order, after any change to models.py – a very common beginner mistake is forgetting one of these two steps.

48. Model Relationships

DatabaseFrequently Tested

Relationships connect tables together – matching the same relational concepts covered generally in the AutoCAD/Tally-style courses, now expressed directly as Django fields.

  • ForeignKey (Many-to-One) – e.g. many Posts belong to one User. on_delete is required, controlling what happens if the related object is deleted: CASCADE (delete this too), SET_NULL (set this field to NULL, requires null=True), PROTECT (block the deletion).
  • ManyToManyField – e.g. a Post can have many Tags, and a Tag can belong to many Posts.
  • OneToOneField – e.g. one User has exactly one Profile.
  • related_name – sets the reverse-access attribute name, e.g. related_name="posts" lets you write user.posts.all() to get every Post by that User.
class Tag(models.Model):
    name = models.CharField(max_length=50)

class Post(models.Model):
    # ... other fields ...
    tags = models.ManyToManyField(Tag, blank=True, related_name="posts")

class Profile(models.Model):
    user = models.OneToOneField(User, on_delete=models.CASCADE, related_name="profile")
    bio = models.TextField(blank=True)

49. QuerySets & CRUD Operations

DatabaseUsed in Every View

CRUD = Create, Read, Update, Delete – the four basic database operations, all done via each Model's .objects manager, returning a "QuerySet" (a lazy, chainable collection of results).

from blog.models import Post, Category

# CREATE
category = Category.objects.create(name="Django")
post = Post.objects.create(title="My First Post", slug="my-first-post",
                             author=some_user, category=category, content="Hello!")

# READ
Post.objects.all()                              # every post
Post.objects.filter(published=True)              # only published posts
Post.objects.get(slug="my-first-post")            # exactly one post (errors if 0 or 2+ match)
Post.objects.filter(title__icontains="django")   # case-insensitive partial match
Post.objects.exclude(published=False)             # everything EXCEPT this condition
Post.objects.order_by("-created_at")              # newest first ("-" reverses the order)
Post.objects.count()                              # just the count, efficiently

# UPDATE
post.title = "An Updated Title"
post.save()                                        # writes the change to the database

# DELETE
post.delete()
  • QuerySets are "lazy" – the actual database query only runs when the results are used (e.g. printed, looped over, or converted to a list), letting you chain multiple filters efficiently.
  • __icontains, __gt, __lt, __in – "field lookups" appended with a double underscore, used to build rich filter conditions.

51. Django Forms

Backend

Django's forms.Form class defines a form's fields in Python, automatically handling HTML rendering AND server-side validation together – far more robust than validating raw HTML form data manually.

# blog/forms.py
from django import forms

class ContactForm(forms.Form):
    name = forms.CharField(max_length=100)
    email = forms.EmailField()
    message = forms.CharField(widget=forms.Textarea)
# In a view:
def contact(request):
    if request.method == "POST":
        form = ContactForm(request.POST)
        if form.is_valid():
            name = form.cleaned_data["name"]     # validated, cleaned data
            email = form.cleaned_data["email"]
            # ... send an email, save to DB, etc ...
            return redirect("thank-you")
    else:
        form = ContactForm()
    return render(request, "contact.html", {"form": form})
<!-- In the template: -->
<form method="post">
  {% csrf_token %}
  {{ form.as_p }}
  <button type="submit">Send</button>
</form>
  • {% csrf_token %} – REQUIRED in every POST form; Django rejects any POST request missing this security token, protecting against Cross-Site Request Forgery attacks (Section 72).
  • form.as_p – renders every field wrapped in a <p> tag automatically; as_table and as_ul are alternatives.

52. ModelForms

BackendUsed Constantly

A ModelForm auto-generates a form directly FROM a Model, matching its fields exactly – avoiding writing the same fields twice (once in the Model, once in the Form). This is what the Blog project's Post and Comment forms actually use.

# blog/forms.py
from django import forms
from .models import Post, Comment

class PostForm(forms.ModelForm):
    class Meta:
        model = Post
        fields = ["title", "slug", "category", "content", "published"]

class CommentForm(forms.ModelForm):
    class Meta:
        model = Comment
        fields = ["body"]
        widgets = {
            "body": forms.Textarea(attrs={"rows": 3, "placeholder": "Write a comment..."})
        }
# In a view, saving a ModelForm creates/updates the actual database object directly:
def post_create(request):
    if request.method == "POST":
        form = PostForm(request.POST)
        if form.is_valid():
            post = form.save(commit=False)   # build the object but don't save yet
            post.author = request.user       # set a field not included in the form
            post.save()                       # now actually save to the database
            return redirect("post-detail", slug=post.slug)
    else:
        form = PostForm()
    return render(request, "blog/post_form.html", {"form": form})
  • commit=False – a very common pattern when the model needs a field (like author) set from the request rather than the form itself, before the final save.

53. Form Validation

Backend

Beyond automatic type checks (e.g. EmailField rejecting invalid emails), custom validation logic is added with clean_<fieldname>() methods.

from django import forms

class ContactForm(forms.Form):
    name = forms.CharField(max_length=100)
    email = forms.EmailField()
    message = forms.CharField(widget=forms.Textarea)

    def clean_name(self):
        name = self.cleaned_data["name"]
        if len(name) < 2:
            raise forms.ValidationError("Name must be at least 2 characters.")
        return name

# Tested directly:
form = ContactForm(data={"name": "A", "email": "bad-email", "message": "hi"})
print(form.is_valid())   # False
print(form.errors)
# {'name': ['Name must be at least 2 characters.'],
#  'email': ['Enter a valid email address.']}
  • clean() (no field name) – for validation that depends on MULTIPLE fields together, e.g. checking a "confirm password" field matches "password".

54. Handling File Uploads

Part I — Advanced Views & Authentication

55. Class-Based Views (CBVs)

BackendFrequently Tested

Class-Based Views express a View as a Python class instead of a function – Django provides many ready-made base classes handling common patterns (list a queryset, show one object, save a form) with far less code than writing the equivalent function-based view.

  • Function-Based Views (FBVs) – more explicit and easier for beginners to trace line-by-line (used in Sections 40, 52).
  • Class-Based Views (CBVs) – less code for standard patterns, and easily extended via inheritance and mixins – the more common choice in larger, real-world Django projects.
  • In urls.py, a CBV is wired up by calling .as_view() on it: path("posts/", PostListView.as_view()).

56. Generic Views

BackendUsed Constantly

Django's built-in "Generic" CBVs cover the most common CRUD patterns almost entirely out of the box.

# blog/cbv_views.py
from django.views.generic import ListView, DetailView, CreateView, UpdateView, DeleteView
from django.contrib.auth.mixins import LoginRequiredMixin
from django.urls import reverse_lazy
from .models import Post
from .forms import PostForm

class PostListView(ListView):
    model = Post
    template_name = "blog/post_list.html"
    context_object_name = "posts"   # the variable name used in the template (default: object_list)
    paginate_by = 5                  # automatic pagination, 5 posts per page

    def get_queryset(self):
        return Post.objects.filter(published=True)   # customize which objects are shown

class PostDetailView(DetailView):
    model = Post
    template_name = "blog/post_detail_cbv.html"

class PostCreateView(LoginRequiredMixin, CreateView):
    model = Post
    form_class = PostForm
    template_name = "blog/post_form.html"

    def form_valid(self, form):
        form.instance.author = self.request.user   # set a field before saving
        return super().form_valid(form)

class PostUpdateView(LoginRequiredMixin, UpdateView):
    model = Post
    form_class = PostForm
    template_name = "blog/post_form.html"

class PostDeleteView(LoginRequiredMixin, DeleteView):
    model = Post
    template_name = "blog/post_confirm_delete.html"
    success_url = reverse_lazy("post-list-cbv")
# blog/urls.py
from .cbv_views import PostListView, PostDetailView, PostCreateView, PostUpdateView, PostDeleteView

urlpatterns = [
    path("cbv/", PostListView.as_view(), name="post-list-cbv"),
    path("cbv/<int:pk>/", PostDetailView.as_view(), name="post-detail-cbv"),
    path("cbv/new/", PostCreateView.as_view(), name="post-create-cbv"),
    path("cbv/<int:pk>/edit/", PostUpdateView.as_view(), name="post-update-cbv"),
    path("cbv/<int:pk>/delete/", PostDeleteView.as_view(), name="post-delete-cbv"),
]
  • LoginRequiredMixin – add as the FIRST base class to require login, automatically redirecting anonymous users to the login page (mixins go before the generic view class in the inheritance list).
  • This exact 5-view pattern (List, Detail, Create, Update, Delete) is so common it's often called the "CRUD views" pattern – expect to write it repeatedly across real projects.

57. Django Sessions & Cookies

Backend

HTTP itself is "stateless" (each request is independent, with no memory of previous ones) – Sessions let Django remember information about a specific visitor ACROSS multiple requests, using a cookie storing a session ID that maps to server-side data.

def set_favorite(request):
    request.session["favorite_category"] = "Django"
    return redirect("post-list")

def show_favorite(request):
    favorite = request.session.get("favorite_category", "None set")
    return render(request, "favorite.html", {"favorite": favorite})
  • Django's login system (Section 58) is itself built on sessions – once logged in, the session remembers request.user on every subsequent request without re-sending credentials.
  • Sessions are stored server-side (in the database by default); only an opaque session ID is stored in the visitor's browser cookie, not the actual data – more secure than storing data directly in a cookie.

A simple custom middleware, for reference:

# blog/middleware.py
import time

class RequestTimingMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        start = time.time()
        response = self.get_response(request)   # process the rest of the request
        duration = time.time() - start
        response["X-Response-Time"] = f"{duration:.3f}s"
        return response

Part J — Building REST APIs with Django REST Framework

61. Introduction to REST & Django REST Framework (DRF)

BackendEssential Modern Skill

A REST API returns raw data (usually JSON) instead of rendered HTML pages – letting a JavaScript frontend (Section 29), a mobile app, or another service consume your Django backend's data directly. DRF is the standard, extremely popular toolkit added on top of Django specifically for building these APIs.

  • REST (Representational State Transfer) – an architectural style where each URL represents a "resource" (e.g. /api/posts/), and HTTP methods (Section 2) determine the action: GET (read), POST (create), PUT/PATCH (update), DELETE (remove).
  • Install with pip install djangorestframework, then add "rest_framework" to INSTALLED_APPS.

62. Serializers

Backend

A Serializer converts Django Model instances into JSON (for API responses) and validates/converts incoming JSON back into Python data (for creating/updating objects) – the API equivalent of a ModelForm (Section 52).

# blog/serializers.py
from rest_framework import serializers
from .models import Post, Comment

class CommentSerializer(serializers.ModelSerializer):
    author = serializers.ReadOnlyField(source="author.username")

    class Meta:
        model = Comment
        fields = ["id", "author", "body", "created_at"]

class PostSerializer(serializers.ModelSerializer):
    author = serializers.ReadOnlyField(source="author.username")
    comments = CommentSerializer(many=True, read_only=True)   # nested serializer

    class Meta:
        model = Post
        fields = ["id", "title", "slug", "author", "content", "created_at", "published", "comments"]
  • ReadOnlyField(source="author.username") – shows the author's username (not their whole user object or just an ID) in the API output, but doesn't accept it as writable input.
  • Nesting CommentSerializer inside PostSerializer automatically includes each post's comments directly in its JSON response.

63. API Views & ViewSets

BackendVery Common Pattern

A ModelViewSet automatically provides ALL standard CRUD API endpoints (list, retrieve, create, update, delete) for a model in one single class – the DRF equivalent of Django's generic CBVs (Section 56), but for APIs.

# blog/api_views.py
from rest_framework import viewsets, permissions
from .models import Post
from .serializers import PostSerializer

class IsAuthorOrReadOnly(permissions.BasePermission):
    """Custom permission: anyone can read, only the author can edit/delete."""
    def has_object_permission(self, request, view, obj):
        if request.method in permissions.SAFE_METHODS:   # GET, HEAD, OPTIONS
            return True
        return obj.author == request.user

class PostViewSet(viewsets.ModelViewSet):
    queryset = Post.objects.filter(published=True)
    serializer_class = PostSerializer
    permission_classes = [permissions.IsAuthenticatedOrReadOnly, IsAuthorOrReadOnly]

    def perform_create(self, serializer):
        serializer.save(author=self.request.user)   # auto-assign the logged-in user

A Router automatically generates all the standard URL patterns for a ViewSet:

# blog/api_urls.py
from rest_framework.routers import DefaultRouter
from .api_views import PostViewSet

router = DefaultRouter()
router.register("posts", PostViewSet, basename="post-api")
urlpatterns = router.urls
# Automatically creates:
#   GET/POST   /posts/           (list all / create one)
#   GET/PUT/PATCH/DELETE /posts/{id}/   (retrieve / update / partial update / delete one)

Tested with real requests:

GET /api/posts/1/          -> 200, JSON detail of post #1, including nested comments

Verified full flow: a client logs in once to get a token, then includes it on every future request:

import requests

# 1. Obtain a token by posting valid credentials
resp = requests.post("http://127.0.0.1:8000/api-token-auth/",
                       data={"username": "alice", "password": "testpass123"})
token = resp.json()["token"]

# 2. Include the token in the Authorization header on every subsequent request
headers = {"Authorization": f"Token {token}"}
resp2 = requests.post("http://127.0.0.1:8000/api/posts/",
                        json={"title": "New Post", "slug": "new-post", "content": "Hello API"},

72. Security Best Practices

BackendFrequently Tested
  • Never run with DEBUG = True in production – it exposes detailed error pages including source code and settings to any visitor who triggers an error.
  • CSRF Protection – enabled by default via CsrfViewMiddleware (Section 60); never disable it just to "make a form work" – fix the actual missing {% csrf_token %} instead.
  • SQL Injection – the Django ORM automatically parameterizes queries, protecting against this by default, AS LONG AS you use the ORM rather than writing raw SQL string concatenation.
  • XSS (Cross-Site Scripting) – Django templates auto-escape variables by default ({{ variable }}), preventing malicious HTML/JS from being injected via user input; only use |safe or mark_safe() when you are certain the content is trustworthy.
  • Password storage – Django's User model automatically hashes passwords (using PBKDF2 by default); never store or compare plain-text passwords yourself.
  • Keep SECRET_KEY out of version control (Section 70) – it's used to cryptographically sign sessions and other security-critical data.

# blog/api_views.py
from rest_framework.decorators import action
from rest_framework.response import Response
from .serializers import CommentSerializer

class PostViewSet(viewsets.ModelViewSet):
    queryset = Post.objects.filter(published=True)
    serializer_class = PostSerializer
    permission_classes = [permissions.IsAuthenticatedOrReadOnly, IsAuthorOrReadOnly]

    def perform_create(self, serializer):
        serializer.save(author=self.request.user)

    @action(detail=True, methods=["post"], permission_classes=[permissions.IsAuthenticated])
    def comments(self, request, pk=None):
        post = self.get_object()
        serializer = CommentSerializer(data=request.data)
        if serializer.is_valid():
            serializer.save(post=post, author=request.user)
            return Response(serializer.data, status=201)
        return Response(serializer.errors, status=400)
