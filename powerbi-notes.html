Part A — Introduction to Power BI

1. What is Business Intelligence?

Business Intelligence (BI) is the process of collecting raw business data from various sources, transforming it into meaningful information, and presenting it through reports and visuals so that people can make informed, data-driven decisions instead of relying on guesswork.

  • Raw data (e.g. sales transactions in a spreadsheet) on its own is hard to interpret at a glance.
  • BI tools turn that raw data into charts, dashboards, and KPIs that instantly show trends, patterns, and outliers.
  • Power BI, Tableau, and Qlik are the three most widely used BI tools in the industry today.

2. What is Power BI?

Power BI is Microsoft's Business Intelligence and data visualization tool, used to connect to many different data sources, clean and shape that data, build a data model, and create interactive reports and dashboards – all without needing to write traditional programming code for most tasks.

  • Free to start (Power BI Desktop is completely free to download and use for building reports).
  • Deeply integrated with other Microsoft products: Excel, SQL Server, Azure, SharePoint, Teams.
  • One of the most in-demand skills for Data Analyst roles worldwide.

3. Power BI Components

Job Relevance

"Power BI" is actually a suite of related products working together – know what each one is for.

  • Power BI Desktop – the free Windows application used to connect to data, transform it, build the data model, write DAX, and design reports. This is where almost all report-building work happens.
  • Power BI Service (app.powerbi.com) – the cloud-based platform where finished reports are published, organized into workspaces, combined into dashboards, and shared with others.
  • Power BI Mobile – apps for iOS/Android/Windows to view reports and dashboards on the go.
  • Power BI Report Server – an on-premises alternative to the Power BI Service, for organizations that cannot store data in the cloud.
  • Power BI Gateway – a bridge that lets the cloud-based Power BI Service securely refresh data from on-premises data sources (Section 83).

4. Installing Power BI Desktop

  • Download free from the Microsoft Store, or from powerbi.microsoft.com – no license/payment needed for Desktop.
  • Requires Windows; there is no native Power BI Desktop for macOS or Linux (a Windows virtual machine or the browser-based Service can be used as workarounds).
  • Sign in with a free Microsoft account to unlock publishing and sharing features (optional for just building reports locally).

5. Power BI Desktop Interface Overview

  • Report View – the main canvas where visuals are placed and arranged into pages, the default view when opening Power BI Desktop.
  • Data View – shows the actual rows and columns of every loaded table, like a spreadsheet grid – used to inspect data and write calculated columns.
  • Model View – shows all loaded tables and the relationships (lines) connecting them – used to build and manage the data model (Part D).
  • Fields Pane (right side) – lists every table and column/measure available to drag onto visuals.
  • Visualizations Pane (right side) – the gallery of chart types, and the formatting options for whichever visual is selected.
  • Switch between these three views using the icons on the far-left vertical toolbar.

6. The Power BI Workflow

Every Power BI project follows the same overall sequence – understanding this flow makes the rest of these notes click into place.

  • 1. Get Data – connect to one or more data sources (Part B).
  • 2. Transform – clean and reshape the data in Power Query Editor (Part C).
  • 3. Model – build relationships between tables (Part D).
  • 4. Calculate – write DAX measures and columns for custom calculations (Part E).
  • 5. Visualize – build charts, tables, and cards onto report pages (Parts F-G).
  • 6. Publish & Share – push the finished report to the Power BI Service and share it with others (Part H).

Part B — Connecting to Data Sources

7. Data Source Types Overview

Power BI can connect to well over 100 different data source types – from simple files to enterprise databases and cloud services.

  • Files – Excel, CSV, Text, XML, JSON, PDF, Folder (importing many files at once).
  • Databases – SQL Server, MySQL, PostgreSQL, Oracle, and many more.
  • Online Services – SharePoint, Salesforce, Google Analytics, Dynamics 365.
  • Other – Web pages, OData feeds, Azure services, blank tables typed manually.

8. Connecting to Excel Files

Most Common Beginner Source

The most common starting point for beginners, since most business data already lives in Excel spreadsheets.

  • Home tab > Get Data > Excel Workbook > browse to the file.
  • The Navigator window then shows every sheet and named table in the file – tick the checkboxes for the ones needed.
  • Click Transform Data to open Power Query Editor first (recommended, to clean data before loading), or Load to import it directly as-is.

9. Connecting to CSV/Text Files

  • Home tab > Get Data > Text/CSV > browse to the file.
  • A preview window shows the detected delimiter (comma, tab, semicolon) and column data types – these can be adjusted before loading.

10. Connecting to a Folder

Combines many files with an identical structure (e.g. one CSV exported per month) into a single, unified table automatically – extremely useful for recurring reports.

  • Home tab > Get Data > Folder > select the folder containing all the files.

11. Connecting to Web Data Sources

  • Home tab > Get Data > Web > paste the URL of a page containing a data table.
  • Power BI scans the page and lists every HTML table it detected, ready to import.

Part C — Power Query Editor: Data Transformation

14. What is Power Query?

Power Query

Power Query is Power BI's data-cleaning and transformation engine – almost every real-world dataset has issues (blank rows, wrong data types, inconsistent text, unwanted columns) that must be fixed BEFORE building visuals, and Power Query is where that cleanup happens.

  • Every action taken (removing a column, changing a type, filtering rows) is recorded as a numbered, reorderable, undoable "Applied Step" – nothing is destructive to the original source file.
  • Behind every action is generated code in the M language (technically "Power Query M"), which can also be written or edited directly for advanced control.
  • The same Power Query engine is also used inside Excel's "Get & Transform" feature.

15. Power Query Editor Interface

Power Query
  • Open it via Home tab > Transform Data (or right-click a query and choose Edit).
  • Queries pane (left) – lists every table/query loaded into the model.
  • Data preview (center) – shows the current state of the selected query's data.
  • Applied Steps pane (right) – the ordered list of every transformation applied so far; click any step to see the data at that point in time, or click the gear icon to edit a step's settings.
  • Formula Bar (top, may need enabling via View tab) – shows the actual M code for the currently selected step.

16. Removing Columns and Rows

Power Query
  • Remove Columns – right-click a column header > Remove, or select multiple columns and use Home > Remove Columns. Removing unneeded columns keeps the model smaller and faster.
  • Remove Rows – Home > Remove Rows offers: Remove Top Rows, Remove Bottom Rows, Remove Duplicates, Remove Blank Rows, and Remove Errors.
// M code generated by removing two columns:
= Table.RemoveColumns(#"Previous Step", {"Notes", "InternalID"})

// M code generated by removing duplicate rows:
= Table.Distinct(#"Previous Step")

17. Changing Data Types

Power QueryVery Common Beginner Fix

Power BI needs to know if a column is Text, Whole Number, Decimal, Date, or True/False – a wrong data type (e.g. a date stored as text) silently breaks sorting, filtering, and DAX calculations.

  • Click the small type icon in the column header (e.g. "ABC" or "1.2") to change it, or right-click > Change Type.
  • Common types: Text, Whole Number, Decimal Number, Currency, Date, Date/Time, True/False.
// M code generated by changing "OrderDate" to Date type:
= Table.TransformColumnTypes(#"Previous Step", {{"OrderDate", type date}})

18. Renaming Columns and Queries

Power Query
  • Double-click a column header (or right-click > Rename) to rename it – use clear, business-friendly names since these appear directly in the Fields pane for report building.
  • Right-click a query name in the Queries pane > Rename, to give the whole table a clearer name.

19. Filtering Rows

Power Query

Click the small dropdown arrow in any column header to filter, just like an Excel AutoFilter – filtering here permanently removes rows from the loaded data, unlike a report-level filter which only hides them from one visual.

// M code generated by filtering to only orders from 2024:
= Table.SelectRows(#"Previous Step", each Date.Year([OrderDate]) = 2024)

20. Sorting Data

Power Query

Use the sort arrows in a column header's dropdown to sort ascending/descending – useful during data cleaning to visually spot issues, though final report sorting is usually controlled separately in the report visuals (Section 77).

21. Split Column

Power Query

Breaks one column into multiple columns – e.g. splitting a "Full Name" column into separate "First Name" and "Last Name" columns.

  • Select the column > Home (or Transform) tab > Split Column > By Delimiter (e.g. a space) or By Number of Characters.
// M code generated by splitting "Full Name" on the space character:
= Table.SplitColumn(#"Previous Step", "Full Name",
    Splitter.SplitTextByDelimiter(" ", QuoteStyle.Csv), {"First Name", "Last Name"})

22. Merge Columns

Power Query

The reverse of Split Column – combines two or more columns into one, with an optional separator (e.g. combining "City" and "State" into "City, State").

  • Select the columns (Ctrl+click for multiple) > Transform tab > Merge Columns.

23. Group By

Power Query

Aggregates rows into summary rows based on one or more grouping columns – similar to a GROUP BY in SQL or a Pivot Table summary.

  • Home tab > Group By > choose the column(s) to group by, and the aggregation (Sum, Average, Count Rows, Min, Max) to calculate per group.
// M code generated grouping by "Region", summing "SalesAmount":
= Table.Group(#"Previous Step", {"Region"}, {{"Total Sales", each List.Sum([SalesAmount]), type number}})

24. Pivot and Unpivot Columns

Power QueryVery Common Real-World Fix

Real-world spreadsheets are very often exported in "wide" format (e.g. one column per month: Jan, Feb, Mar...), but Power BI works far better with "tall/long" format (one row per Month + Value pair). Unpivot is one of the most useful, frequently-needed transformations for beginners to master.

  • Unpivot Columns – select the columns to unpivot (e.g. Jan, Feb, Mar) > Transform tab > Unpivot Columns – turns them into two new columns: "Attribute" (the original column name) and "Value".
  • Pivot Column – the reverse operation, turning unique values from one column into new separate columns.
// Before Unpivot:  Product | Jan | Feb | Mar
//                  Widget  | 100 | 120 | 90

// M code generated by unpivoting Jan, Feb, Mar:
= Table.UnpivotOtherColumns(#"Previous Step", {"Product"}, "Month", "Sales")

// After Unpivot:   Product | Month | Sales
//                  Widget  | Jan   | 100
//                  Widget  | Feb   | 120
//                  Widget  | Mar   | 90

25. Append Queries

Power Query

Stacks two or more tables with the SAME columns on top of each other into one combined table – e.g. combining "Sales_Jan" and "Sales_Feb" tables into one "Sales_All" table. Equivalent to a SQL UNION.

  • Home tab > Append Queries > choose "Two Tables" or "Three or More Tables".
// M code generated appending "Sales_Feb" onto "Sales_Jan":
= Table.Combine({Sales_Jan, Sales_Feb})

26. Merge Queries (Joins)

Power QueryVery Common Real-World Fix

Combines two tables SIDE BY SIDE, matching rows based on a common column – the Power Query equivalent of a SQL JOIN. Different from Append (which stacks rows), Merge adds columns.

  • Home tab > Merge Queries > select the second table, then click the matching column in both tables.
  • Join Kind options: Left Outer (all rows from first table, matches from second), Right Outer, Full Outer, Inner (only matching rows in both), Left Anti (only rows from first table with NO match), Right Anti.
// M code generated merging "Sales" with "Products" on "ProductID", Left Outer join:
= Table.NestedJoin(Sales, {"ProductID"}, Products, {"ProductID"}, "Products", JoinKind.LeftOuter)
// After this step, expand the new "Products" column to pull in specific columns like "ProductName"

27. Conditional Column

Power Query

Creates a new column using simple if/then/else logic built through a visual dialog – no M code writing required, ideal for beginners.

  • Add Column tab > Conditional Column > define one or more "If [column] [operator] [value] Then [output]" rules, with a final Else.
// M code generated by a conditional column categorizing sales amount:
= Table.AddColumn(#"Previous Step", "Sales Category", each
    if [SalesAmount] >= 10000 then "High"
    else if [SalesAmount] >= 5000 then "Medium"
    else "Low")

28. Custom Column (M Formula)

Power Query

Creates a new column using a typed M formula, for logic beyond what the Conditional Column dialog can express – the natural next step once comfortable with basic Power Query.

  • Add Column tab > Custom Column > give it a name and type the M formula, referencing other columns with square brackets.
// Custom Column formula calculating profit:
= [SalesAmount] - [CostAmount]

// Custom Column formula combining two text columns:
= [FirstName] & " " & [LastName]

29. Replace Values & Fill Down/Up

Power Query
  • Replace Values – right-click a column > Replace Values, to find-and-replace specific values (e.g. replacing "N/A" with null, or fixing a misspelled category name).
  • Fill Down / Fill Up – Transform tab > Fill – copies a value downward (or upward) to replace blank cells below it, common when cleaning data exported from merged Excel cells (e.g. a Region name only appearing on the first row of each group).

30. Query Parameters

Power Query

Reusable values (e.g. a file path, a start date, a server name) that can be referenced inside multiple queries – changing the parameter once updates every query using it, instead of editing each query's source individually.

  • Home tab > Manage Parameters > New Parameter – define its name, type, and current value.

31. Applied Steps & Query Dependencies

Power Query
  • Every transformation is a separate, named step in the Applied Steps pane – steps can be renamed, reordered (drag), or deleted (click the X) individually.
  • Click the gear icon next to a step to reopen its settings dialog and edit it without redoing the action.
  • A query can reference another query as its source (right-click > Reference), building a chain of dependent queries – useful for reusing a common cleaning step across multiple final tables.

Part D — Data Modeling

32. What is Data Modeling?

Data Modeling is the process of connecting multiple loaded tables together through relationships, so that Power BI understands how they relate – enabling one visual to combine data from several tables correctly and automatically.

  • Without a correct model, filtering by one table (e.g. selecting a Region) will not correctly filter another related table (e.g. Sales), producing wrong totals.
  • A good model is the foundation everything else (DAX, visuals) depends on – time invested here pays off throughout the whole report.

33. Star Schema vs Snowflake Schema

Best Practice

Two common ways to organize a data model – Power BI is specifically optimized for, and Microsoft explicitly recommends, the Star Schema.

  • Star Schema – one central Fact table connected directly to several surrounding Dimension tables, forming a star shape. Simpler, faster, and easier to write DAX against – the recommended standard.
  • Snowflake Schema – dimension tables are further broken down into related sub-dimension tables (e.g. Product → Category → Department), creating a more normalized but more complex web of relationships.

34. Fact Tables vs Dimension Tables

Frequently Tested Concept
  • Fact Table – contains the measurable, numeric business events/transactions (e.g. a Sales table with OrderDate, ProductID, CustomerID, Quantity, SalesAmount). Usually the largest table, with many rows.
  • Dimension Table – contains descriptive attributes used to filter and group the facts (e.g. a Products table with ProductID, ProductName, Category; or a Customers table; or a Date table). Usually smaller, with fewer rows.
  • Rule of thumb: if a column is something you'd SUM or COUNT, it likely belongs in a Fact table; if it's something you'd filter or group BY, it likely belongs in a Dimension table.

35. Creating Relationships

A relationship links two tables together using a common column (a key), so filtering one table correctly filters the other.

  • Switch to Model View > drag a field from one table directly onto the matching field in another table to create the relationship visually.
  • Or use Home tab > Manage Relationships > New, and select the two tables and matching columns from dropdowns.
  • Power BI often auto-detects and creates relationships automatically when tables are first loaded, based on matching column names – always verify these are correct rather than assuming.

36. Cardinality (One-to-Many, Many-to-Many, One-to-One)

Frequently Tested

Cardinality describes how many matching rows exist on each side of a relationship.

  • One-to-Many (1:*) – the most common type; one row in a Dimension table (e.g. one Product) relates to many rows in the Fact table (e.g. many Sales of that product).
  • Many-to-Many (*:*) – both tables can have multiple matching rows on each side; supported but should be used carefully, as it can produce ambiguous or unexpected results if not designed deliberately.
  • One-to-One (1:1) – each row in one table matches exactly one row in the other; relatively rare, often signals the two tables could simply be merged into one.

37. Cross Filter Direction

Frequently Tested

Controls which direction filtering "flows" across a relationship.

  • Single direction (the default, and generally recommended) – filtering the "one" side (Dimension table) filters the "many" side (Fact table), but not the reverse.
  • Both directions (bi-directional) – filtering flows both ways; needed for some specific scenarios (e.g. certain many-to-many designs), but can cause performance issues or ambiguous filtering if overused – use only when genuinely required.

38. Managing Relationships

  • Home tab > Manage Relationships shows every relationship in the model in one list, allowing edits, deletion, or activation/deactivation.
  • Only ONE relationship between a given pair of tables can be "Active" (solid line in Model View) at a time; any additional relationships between the same two tables are "Inactive" (dashed line) and must be explicitly invoked in DAX using USERELATIONSHIP.

39. Hierarchies

A Hierarchy groups related columns into a drill-down structure, e.g. Year → Quarter → Month → Day, or Country → State → City – letting a report user drill from a high-level summary down into more and more detail on the same visual.

  • In the Fields pane, right-click a column > "Create Hierarchy", then drag additional columns into it in the desired drill order.
  • Power BI automatically creates a built-in Date Hierarchy (Year/Quarter/Month/Day) for any column formatted as a Date.

Part E — DAX Fundamentals

40. What is DAX?

DAX

DAX (Data Analysis Expressions) is Power BI's formula language, used to create custom calculations on top of the data model – similar in appearance to Excel formulas, but designed to work across entire tables and relationships rather than individual cells.

  • Every DAX formula returns a single value or a table, built from functions, operators, and references to columns/tables.
  • DAX is arguably the single most important, and most challenging, skill for a beginner to master in Power BI – this Part builds it up function by function.
  • All examples in this Part assume a Sales table (OrderDate, ProductID, CustomerID, Region, Quantity, UnitPrice, SalesAmount) related to Products and Customers dimension tables, following the star schema from Part D.

41. Calculated Columns vs Measures

DAXFrequently Tested

The most important distinction in all of DAX – choosing the wrong one is the most common beginner mistake.

  • Calculated Column – computed ROW BY ROW, at the time data is loaded/refreshed, and stored physically in the table (taking up memory). Used when you need a new column to filter, group, or slice by (e.g. categorizing each sale as "High" or "Low" value).
  • Measure – computed ON THE FLY, only when used in a visual, based on whatever filters are currently applied (e.g. from slicers, other visuals). Not stored in the table – far more memory-efficient. Used for almost all aggregations (totals, averages, ratios).
  • Rule of thumb: if the result should change depending on what's selected/filtered in a report, use a Measure. If it's a fixed, row-level classification, use a Calculated Column.
-- Calculated Column example (creates a new column with a value per row):
Order Year = YEAR(Sales[OrderDate])

-- Measure example (creates a single aggregated value, sensitive to filters):
Total Sales = SUM(Sales[SalesAmount])

42. Basic Aggregation Functions

DAX

The most commonly used functions, summarizing a column across many rows into one number – nearly every report uses several of these as Measures.

Total Sales = SUM(Sales[SalesAmount])
Average Sale = AVERAGE(Sales[SalesAmount])
Total Orders = COUNTROWS(Sales)              -- counts rows in the table
Customer Count = DISTINCTCOUNT(Sales[CustomerID])
Max Sale = MAX(Sales[SalesAmount])
Min Sale = MIN(Sales[SalesAmount])
Non-Blank Notes = COUNTA(Sales[Notes])       -- counts non-blank cells (any type)

43. Logical Functions (IF, AND, OR, SWITCH)

DAX
-- IF: basic conditional logic
Sale Size = IF(Sales[SalesAmount] > 1000, "Large", "Small")

-- Nested IF using AND / OR for multiple conditions
Priority = IF(
    AND(Sales[SalesAmount] > 1000, Sales[Region] = "East"),
    "High Priority",
    "Normal"
)

-- SWITCH: cleaner than many nested IFs when checking one value against several options
Size Category = SWITCH(
    TRUE(),
    Sales[SalesAmount] < 100, "Small",
    Sales[SalesAmount] < 1000, "Medium",
    "Large"
)

44. Text Functions

DAX
Full Name = Customers[FirstName] & " " & Customers[LastName]   -- & concatenates text
Full Name Alt = CONCATENATE(Customers[FirstName], Customers[LastName])
Upper Region = UPPER(Sales[Region])
Lower Region = LOWER(Sales[Region])
First 3 Chars = LEFT(Customers[CustomerID], 3)
Last 4 Chars = RIGHT(Customers[Phone], 4)
Middle Chars = MID(Customers[Code], 2, 3)     -- starts at position 2, takes 3 characters
Trimmed = TRIM(Customers[City])                -- removes extra leading/trailing spaces
Text Length = LEN(Customers[FirstName])

45. Date & Time Functions

DAX
Current Date = TODAY()
Order Year = YEAR(Sales[OrderDate])
Order Month = MONTH(Sales[OrderDate])
Order Month Name = FORMAT(Sales[OrderDate], "MMMM")
Days Since Order = DATEDIFF(Sales[OrderDate], TODAY(), DAY)
Order Quarter = "Q" & QUARTER(Sales[OrderDate])

46. Creating a Date Table

DAXBest Practice

A dedicated Date table (one row per calendar day, related to every date column in the model) is a Power BI best practice, required for Time Intelligence functions (Section 52) to work correctly.

  • Create with a DAX table function, then mark it as the official "Date Table" (Table Tools > Mark as Date Table) so time intelligence functions know to use it.
DateTable = CALENDAR(DATE(2023,1,1), DATE(2025,12,31))

-- Then add helper columns for grouping/filtering:
Year = YEAR(DateTable[Date])
Month Name = FORMAT(DateTable[Date], "MMMM")
Month Number = MONTH(DateTable[Date])

47. The CALCULATE Function

DAXMost Important DAX Function

CALCULATE is the single most powerful and important function in all of DAX – it evaluates an expression while overriding or adding filters to the current filter context. Nearly every advanced DAX formula uses CALCULATE somewhere.

  • Syntax: CALCULATE(expression, filter1, filter2, ...) – the expression is usually an aggregation; the filters add or replace the current context.
-- Total sales, but ONLY for the East region, regardless of what's selected in the report:
East Sales = CALCULATE(
    SUM(Sales[SalesAmount]),
    Sales[Region] = "East"
)

-- Total sales for the current selection, but ALWAYS in year 2024:
Sales 2024 = CALCULATE(
    SUM(Sales[SalesAmount]),
    DateTable[Year] = 2024
)

48. The FILTER Function

DAX

FILTER returns a TABLE containing only the rows that meet a condition – used inside CALCULATE (or other functions expecting a table) when a simple column comparison isn't enough (e.g. comparing two columns to each other).

-- Total sales only from orders where Quantity is greater than 5:
Bulk Order Sales = CALCULATE(
    SUM(Sales[SalesAmount]),
    FILTER(Sales, Sales[Quantity] > 5)
)

49. ALL & ALLEXCEPT Functions

DAX

Used to deliberately REMOVE filters, most commonly to calculate a "% of total" that doesn't get affected by the very filters being applied to the current row/visual.

-- Grand total sales, ignoring any Region/Product filters currently applied:
Grand Total Sales = CALCULATE(
    SUM(Sales[SalesAmount]),
    ALL(Sales)
)

-- % of Total: this row's sales divided by the grand total
Percent of Total = DIVIDE(SUM(Sales[SalesAmount]), [Grand Total Sales])

-- ALLEXCEPT: remove all filters EXCEPT the ones on the listed column(s)
Sales by Region Only = CALCULATE(
    SUM(Sales[SalesAmount]),
    ALLEXCEPT(Sales, Sales[Region])
)

50. RELATED & RELATEDTABLE Functions

DAX
  • RELATED – pulls a single value from a related table on the "one" side of a relationship, into a calculated column on the "many" side. Used in calculated columns.
  • RELATEDTABLE – the reverse: pulls the related rows from the "many" side into an expression on the "one" side, returning a table.
-- In the Sales table (many side), pull the Category from the related Products table (one side):
Product Category = RELATED(Products[Category])

-- In the Products table (one side), count how many sales rows relate to each product:
Times Sold = COUNTROWS(RELATEDTABLE(Sales))

51. Variables in DAX (VAR / RETURN)

DAXBest Practice

Variables store the result of an expression under a name, which can then be reused later in the same formula – making complex DAX both easier to read and faster to calculate (since the value is computed only once, not repeated).

Profit Margin % =
VAR TotalRevenue = SUM(Sales[SalesAmount])
VAR TotalCost = SUM(Sales[Cost])
VAR Profit = TotalRevenue - TotalCost
RETURN
    DIVIDE(Profit, TotalRevenue)

52. Time Intelligence Functions

DAXFrequently Tested

A family of built-in functions for common date-based comparisons, which require a proper Date Table (Section 46) marked and related to work correctly.

-- Year-to-Date total:
Sales YTD = TOTALYTD(SUM(Sales[SalesAmount]), DateTable[Date])

-- Same period, one year earlier (for year-over-year comparison):
Sales LY = CALCULATE(
    SUM(Sales[SalesAmount]),
    SAMEPERIODLASTYEAR(DateTable[Date])
)

-- Generic shift by any interval, using DATEADD:
Sales Prior Month = CALCULATE(
    SUM(Sales[SalesAmount]),
    DATEADD(DateTable[Date], -1, MONTH)
)

53. Common DAX Patterns

DAXInterview Favorite

Three patterns that combine the functions above and appear constantly in real dashboards and interviews.

-- Year-over-Year Growth %:
YoY Growth % =
VAR CurrentSales = SUM(Sales[SalesAmount])
VAR PriorYearSales = CALCULATE(SUM(Sales[SalesAmount]), SAMEPERIODLASTYEAR(DateTable[Date]))
RETURN
    DIVIDE(CurrentSales - PriorYearSales, PriorYearSales)

-- Running Total (cumulative sum over time):
Running Total =
CALCULATE(
    SUM(Sales[SalesAmount]),
    FILTER(ALL(DateTable), DateTable[Date] <= MAX(DateTable[Date]))
)

-- Rank within the current context (e.g. rank products by sales):
Product Rank =
RANKX(ALL(Products[ProductName]), [Total Sales])

54. DAX Context: Row Context vs Filter Context

DAXConceptually Hardest Topic

Understanding "context" is what separates a beginner from an intermediate DAX writer – every DAX formula is evaluated within one (or both) of these two contexts.

  • Row Context – exists when a formula is evaluated one row at a time (as in a Calculated Column, or inside iterator functions like FILTER/SUMX). DAX "knows" which row it's currently on.
  • Filter Context – the set of filters currently applied to a calculation (from slicers, visual rows/columns, or CALCULATE) when a Measure is evaluated. This is why the same Measure formula shows a different number in every cell of a Matrix visual.
  • CALCULATE's special power is that it can transform Row Context into Filter Context – this is precisely why it's so central to advanced DAX.

Part F — Visualizations

55. Introduction to Visualizations

Visuals

A visual is any chart, table, or card placed on a report page. Building one always follows the same basic pattern: click a visual type in the Visualizations pane, then drag fields from the Fields pane into its Values/Axis/Legend wells.

  • Choosing the RIGHT visual for the data and question being asked is as important as building it correctly – this Part covers when to use each type.

56. Bar & Column Charts

Visuals

The most common and easiest-to-read chart for comparing values across categories.

  • Clustered/Stacked Column Chart – vertical bars; best for comparing values across a small-to-medium number of categories, especially over time (left-to-right reads naturally as a timeline).
  • Clustered/Stacked Bar Chart – horizontal bars; best when category names are long (they read left-to-right without being squeezed), or when there are many categories to list.
  • "Stacked" shows parts of a whole within each bar; "Clustered" shows separate side-by-side bars per category, easier for direct comparison between series.

57. Line Charts

Visuals

Best for showing a trend over a continuous range, almost always time (e.g. Sales by Month) – the connecting line emphasizes the direction and rate of change, which bars do not show as clearly.

58. Pie & Donut Charts

Visuals

Show each category's proportion of a whole. Best practice: use only with a SMALL number of categories (5 or fewer) – with many slices, a bar chart is almost always easier to read accurately.

59. Tables and Matrix

Visuals
  • Table – a simple flat grid of rows and columns, like a spreadsheet; good for showing detailed, row-level data.
  • Matrix – like a Pivot Table in Excel; supports both rows AND columns as groupings, with automatic subtotals, and supports drill-down (Section 72) into hierarchies.

60. Cards & KPI Visuals

Visuals
  • Card – displays one single number prominently (e.g. Total Sales), great for headline metrics at the top of a dashboard.
  • Multi-row Card – displays several single values together in a list.
  • KPI Visual – displays one value against a target/goal, with a trend indicator (arrow up/down) and a small trendline showing progress over time.

61. Maps

Visuals
  • Map (bubble map) – plots data as sized circles/bubbles at geographic points (e.g. cities, countries).
  • Filled Map (Choropleth) – shades entire geographic regions (e.g. states/countries) by color intensity based on a value.
  • Requires a geographic column (Country, State, City, Postal Code) recognized by Power BI's geocoding – setting the column's Data Category (right-click > Data Category) improves accuracy.

62. Treemap

Visuals

Shows hierarchical, proportional data as nested rectangles – rectangle size represents value, making it easy to spot the largest contributors at a glance, similar in purpose to a pie chart but scaling better to more categories.

63. Scatter Chart

Visuals

Plots two numeric measures against each other (X and Y axis) to reveal correlation or clustering patterns – can add a third measure as bubble size, and a category as "Play Axis" to animate change over time.

64. Waterfall Chart

Visuals

Shows how a starting value is increased and decreased by a sequence of positive/negative changes to reach a final value – ideal for showing profit bridges (Revenue → minus Costs → equals Profit) or month-over-month changes.

65. Gauge Chart

Visuals

Shows a single value against a minimum, maximum, and target, displayed as a needle on a dial – commonly used for goal-tracking metrics like "% of Sales Target Achieved".

66. Slicers

Visuals

A visual filter control placed directly on the report canvas, letting the report VIEWER interactively filter every other visual on the page by clicking a value (e.g. a Region slicer with buttons for East/West/North/South).

  • Can be a list, dropdown, or (for numeric/date fields) a between-range slider.
  • Slicers can be synced to apply across multiple report pages at once (Section 76).

67. Custom Visuals from AppSource

Visuals

Beyond the built-in visual types, thousands of additional visuals (word clouds, advanced charts, custom KPI cards) are available free from Microsoft AppSource.

  • Visualizations pane > "..." (Get more visuals) > search AppSource, or import a downloaded .pbiviz file directly.
  • Use official/well-reviewed visuals when possible, since custom visuals can carry data privacy or performance considerations in a corporate environment.

Part G — Formatting & Interactivity

68. Formatting Visuals

Visuals

Every visual has a Format pane (the paint-roller icon in Visualizations) with extensive options to make it clear and presentable.

  • Title – text, font, size, background, alignment.
  • Data Labels – toggle on to show the actual value on/near each bar, point, or slice.
  • Colors – set per-series or per-data-point colors under "Data colors".
  • Axis – control gridlines, min/max range, axis title visibility.

69. Conditional Formatting

Visuals

Automatically changes a visual's appearance (background color, font color, data bars, icons) based on the underlying value – makes tables and matrices far easier to scan for outliers at a glance.

  • On a Table/Matrix column: click the column's formatting options > Conditional Formatting > choose Background Color, Font Color, Data Bars, or Icons.
  • Rules can be based on a color scale (e.g. red-yellow-green by value), fixed rules, or another measure entirely.

70. Tooltips

Visuals

The popup that appears when hovering over a data point – can be customized to show extra fields beyond the default, or replaced entirely with a custom mini-report page ("Report Page Tooltip") for a richer hover preview.

71. Visual-Level, Page-Level & Report-Level Filters

Frequently Tested

The Filters pane has three sections, controlling the SCOPE a filter applies to – a commonly tested distinction.

  • Filters on this visual – applies only to the one selected visual.
  • Filters on this page – applies to every visual on the current report page.
  • Filters on all pages – applies across the entire report, every page.
  • Filters can be locked (so report viewers can't change them) or left open for interactive exploration.

72. Drill Down & Drill Up

Visuals

When a visual uses a Hierarchy (Section 39), small drill arrows appear, letting a viewer click into the next level of detail (e.g. from Year down to Quarter, then Month) directly within the same visual, without navigating to a different page.

  • The double-down-arrow icon enables "drill down one level for all"; the single-down-arrow drills into just the clicked data point.

73. Drillthrough Pages

Visuals

A special report page configured to show detailed information about ONE specific selected item (e.g. right-click a Product in a summary chart > Drillthrough > "Product Details" page, which then filters entirely to that one product).

  • Set up by dragging a field into the "Drillthrough" well in the Format pane of the target page.
  • A "Back" button is added automatically, to return to the originating page.

74. Bookmarks & Selection Pane

Visuals
  • Bookmarks – save the exact current state of a report page (filter selections, which visuals are visible, sort order) so it can be instantly recalled later, e.g. by a button – used to build guided, presentation-style navigation through a report.
  • Selection Pane – lists every object on the page and lets you show/hide them individually, useful for building bookmark-driven "toggle" effects (e.g. switching between two different chart views on the same spot).

75. Buttons & Navigation

Visuals

Buttons can be added (Insert tab > Buttons) and configured with an Action (e.g. "Page Navigation", "Bookmark", or "Back") to build a custom, app-like navigation experience across report pages.

76. Syncing Slicers Across Pages

Visuals

By default, a slicer only filters visuals on its own page. The Sync Slicers pane (View tab > Sync Slicers) allows one slicer's selection to apply across multiple (or all) report pages at once, keeping filter selections consistent as a viewer navigates the report.

77. Sorting Visuals

Visuals

Every visual can be sorted independently of how the underlying data was cleaned/sorted in Power Query – this is the "final report sorting" controlled directly on each visual, referenced back in Section 20.

  • Select a visual > click the "..." (More options) menu > "Sort by" > choose the field, then toggle ascending/descending.
  • For a chart/table axis, this determines the left-to-right or top-to-bottom order of categories – e.g. sorting a bar chart by the measure value (largest first) instead of alphabetically by category name.
  • A column can also be sorted "by another column" (right-click a column in the Fields pane > Sort by Column) – e.g. sorting "Month Name" (Jan, Feb, Mar...) chronologically instead of alphabetically, by linking it to a numeric Month Number column.

Part H — Power BI Service (Cloud)

78. Introduction to Power BI Service

Service

The Power BI Service (app.powerbi.com) is the cloud platform where reports built in Desktop are published, so they can be viewed in a browser, shared with colleagues, refreshed on a schedule, and combined into dashboards – Desktop is for BUILDING, the Service is for SHARING and CONSUMING.

  • A free Power BI account allows creating a personal workspace; sharing content with others generally requires a Power BI Pro license (or Premium capacity for the organization).

79. Publishing Reports to the Service

Service
  • In Power BI Desktop: Home tab > Publish > sign in > choose the destination workspace.
  • This uploads both the report (the visuals/pages) AND the underlying dataset (the data model) as a linked pair to the Service.
Home tab -> Publish
Select a destination: "Sales Analytics" workspace
Click "Select" -> wait for upload to complete -> click the link to open in browser

80. Workspaces

Service

A Workspace is a container in the Service for organizing related reports, datasets, and dashboards – similar to a folder, but with its own set of members and permission levels.

  • My Workspace – a personal, private area every user gets automatically, for individual work.
  • App Workspaces – shared, collaborative workspaces for a team or department, with defined roles: Admin, Member, Contributor, Viewer.

81. Dashboards vs Reports

ServiceFrequently Tested

Two related but distinct concepts, only in the Service (Desktop only has Reports) – a commonly tested distinction.

  • Report – the multi-page, fully interactive set of visuals built in Desktop, with working filters/slicers/drillthrough – exists in both Desktop and the Service.
  • Dashboard – a SINGLE page, built only in the Service, composed of "tiles" PINNED from one or more different reports (even from different datasets) – a single-screen, high-level summary view. Dashboard tiles are mostly static (click one to jump to the full underlying report).

82. Sharing Reports & Dashboards

Service
  • Share – grants specific individuals or groups direct access to view (and optionally edit) a report/dashboard.
  • Publish to Web – generates a public, embeddable link viewable by anyone with the URL, with NO login required – use with caution, only for genuinely public, non-sensitive data.
  • Workspace-level access (Section 80) is often preferred over sharing individual reports, for easier ongoing permission management.

83. Power BI Gateway (On-Premises Data Gateway)

Service

A small application installed on a machine within an organization's own network, acting as a secure bridge that lets the cloud Power BI Service refresh data from on-premises sources (a local SQL Server, an on-premises file share) that the cloud cannot reach directly.

  • Personal Gateway – for one user's own scheduled refreshes on their own machine.
  • Standard (Enterprise) Gateway – a shared, centrally managed gateway supporting many users and data sources across an organization.
  • Without a Gateway, a dataset connected to any on-premises source can only be refreshed manually within Desktop, not automatically in the cloud.

84. Scheduled Refresh

Service

Automatically re-imports the latest data from the source(s) on a defined schedule (e.g. daily at 6 AM), so a published report stays up to date without anyone manually republishing it.

  • Configured in the Service: Dataset > Settings > Scheduled Refresh – set frequency and time(s) of day.
  • Refresh frequency limits depend on license: Pro allows up to 8 refreshes/day; Premium capacity allows up to 48/day.
  • Only relevant for "Import" mode datasets (Section 13) – DirectQuery/Live Connection datasets query the source live, so there's nothing to "refresh" in the same sense.

85. Row-Level Security (RLS)

ServiceFrequently Tested

Restricts which ROWS of data different users can see within the SAME published report, based on their identity – e.g. a Regional Manager for "East" only sees East region data, while an Admin sees everything, all from one single report.

  • Defined in Desktop: Modeling tab > Manage Roles > create a role (e.g. "East Manager") with a DAX filter expression, e.g. [Region] = "East".
  • After publishing, assign specific users/groups to each role in the Service: Dataset > Security.
-- RLS DAX filter expression for a role named "East Manager", applied to the Sales table:
[Region] = "East"

-- A more dynamic version using the logged-in user's email, matched against a mapping table:
[UserEmail] = USERPRINCIPALNAME()

86. Power BI Mobile App

Service

The mobile apps (iOS/Android/Windows) let users view published reports and dashboards, receive data-driven alerts (e.g. notify me if Sales drops below a threshold), and even annotate/share a visual directly from their phone.

87. Power BI Apps (Packaged App Workspaces)

Service

A "distribution" feature that packages the reports/dashboards from a Workspace into a clean, read-only, app-like experience for end users to install – hiding the editing/workspace clutter and presenting only a polished, organized set of content, ideal for distributing finished reports company-wide.

Part I — Best Practices & Performance

88. Data Modeling Best Practices

Best Practice
  • Always aim for a Star Schema (Section 33) – keep dimension tables small and simple, and put all measurable numbers in one central fact table.
  • Remove columns you don't actually need in Power Query (Section 16) BEFORE loading – every unused column still consumes memory and slows down refresh.
  • Use a dedicated Date Table (Section 46) rather than relying only on the auto-generated date hierarchies, especially once Time Intelligence is needed.
  • Prefer Measures over Calculated Columns whenever the result depends on filtering (Section 41) – Measures are calculated on demand and don't bloat the model's stored size.
  • Set correct data types for every column (Section 17) – a numeric column stored as Text cannot be summed and will silently produce wrong/blank results in visuals.

89. DAX Performance Tips

Best Practice
  • Use DIVIDE(numerator, denominator) instead of a plain / division – DIVIDE gracefully returns blank (or a specified alternate value) instead of an error when dividing by zero.
  • Use Variables (Section 51) to avoid recalculating the same expression multiple times within one formula.
  • Avoid using bi-directional cross-filtering (Section 37) unless genuinely necessary – it can slow down calculations across a large model.
  • Prefer COUNTROWS(table) over COUNT(column) when simply counting rows – it's a lighter, more direct operation.
  • Avoid calculated columns that could instead be done once in Power Query (during data load) – Power Query transformations are generally more efficient than row-by-row DAX calculated columns for the same result.

90. Report Design Best Practices

Best Practice
  • Keep each report page focused on one clear question or audience – avoid cramming every possible chart onto a single page.
  • Place the most important KPI Cards at the top-left, since that's where a viewer's eye naturally goes first.
  • Use consistent colors for the same category across every visual in the report (e.g. "East" region is always the same shade of blue everywhere).
  • Avoid pie charts with more than 5 slices (Section 58) – use a bar chart instead for easier comparison.
  • Always add clear titles and axis labels – a chart with no context is not self-explanatory to a viewer seeing it for the first time.
  • Test the report's slicers and filters as an actual end user would, not just as the report's own designer, to catch confusing or broken interactions.

Assignment 3 — Write Core DAX Measures for a Sales Dashboard

DAX

Task: Write measures for Total Sales, Total Cost, Profit, Profit Margin %, Average Order Value, and Total Orders.

Solution 
Total Sales = SUM(Sales[SalesAmount])

Total Cost = SUM(Sales[Cost])

Total Profit = [Total Sales] - [Total Cost]

Profit Margin % = DIVIDE([Total Profit], [Total Sales])

Total Orders = COUNTROWS(Sales)

Average Order Value = DIVIDE([Total Sales], [Total Orders])

-- Test each by adding them to Card visuals, then add a Region slicer

Assignment 4 — Time Intelligence: YTD and YoY Growth

DAX

Task: Create a proper Date table, mark it as the official date table, then write measures for Year-to-Date Sales and Year-over-Year Growth %.

Solution 
1. Create the Date table:
   New Table = CALENDAR(DATE(2023,1,1), DATE(2025,12,31))

2. Add helper columns to it:
   Year = YEAR('New Table'[Date])
   Month Name = FORMAT('New Table'[Date], "MMMM")

3. Rename the table to "DateTable". In Model View, relate
   DateTable[Date] (one side) to Sales[OrderDate] (many side).

4. Select DateTable -> Table Tools tab -> Mark as Date Table -> choose the Date column.

5. Write the measures:
Sales YTD = TOTALYTD([Total Sales], DateTable[Date])

Sales Same Period Last Year =
CALCULATE([Total Sales], SAMEPERIODLASTYEAR(DateTable[Date]))

YoY Growth % =
VAR CurrentSales = [Total Sales]
VAR PriorYear = [Sales Same Period Last Year]
RETURN
    DIVIDE(CurrentSales - PriorYear, PriorYear)

6. Test by adding DateTable[Year] and DateTable[Month Name] to a Matrix
   row, with all three measures as values - Sales YTD should accumulate
   within each year and reset at the next.
